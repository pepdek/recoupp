# DECISIONS.md (defaults I chose; override any)

1. **Repo at `~/recoup`**, git-initialized in Slice 1. Working name "Recoup" kept as placeholder only.
2. **Dedicated Supabase project**, not the shared LawStack project. Sensitive PII of seniors should not share a blast radius with other products. (Needs your OK on cost, see questions.)
3. **Live Stripe mode stays off** until COMPLIANCE_CHECKLIST items are cleared; test mode everywhere until then.
4. **Pricing/guarantees as written:** $99/household (100 min), $149 B2C, 5x guarantee, $1,000 B2C refund threshold. B2B 50% at signup via invoice 1, 50% at household 50 via invoice 2 (triggered by enrolled-count, I send it manually from admin in v1, not automatically).
5. **Rule DSL is minimal:** YAML conditions with all/any/not and comparison ops over household facts. No scripting, no expression engine library.
6. **Value ranges** stored as low/likely/high per program; cash-equivalent total reported separately from avoided-cost items (Medicaid/LTSS coverage), so the 5x guarantee test uses cash-equivalent verified value only. This is a business-definition choice for the contract; flag to your attorney.
7. **Roles:** Postgres RLS keyed off `auth.uid()` + a `role` claim; sponsor viewers see only aggregates unless the household's consent row has `share_with_org = true`.
8. **PDFs:** pdf-lib for fillable public forms, HTML answers sheet otherwise. No SSN fields ever populated.
9. **Email:** Resend (magic link, receipts via Stripe, reminders). SMS deferred.
10. **Extraction model:** Claude via Anthropic API, structured output, every value `unconfirmed` until confirmed.
11. **Analytics:** own `events` table (funnel + kill criteria), no third-party tracker, so no PII leaves the stack.
12. **Home market first:** Pierce County property-tax and Tacoma Public Utilities rules go first among local programs.
13. **Unverified = hidden:** any program with `confidence: needs_review` runs through the reviewer queue and is never auto-shown.
14. **Intake = one topic per screen** (income/bills have several fields on one screen) rather than strictly one field per screen; keeps the flow to ~10 screens. Revisit if drop-off data says otherwise.
15. **Consents** are insert-only (updates blocked); revoking/changing = new row. They are deleted with the household on a delete request; the deletion itself is kept in `audit_log` (no PII, just ids).
16. **Clients write audit rows only via `log_event()`** (actor forced to `auth.uid()`); `audit_log` has no client insert policy.
17. **`owner_id`/`org_id` on households can't be changed by clients** (column-level grants); sponsor-linked households arrive in Slice 6 via the white-label link.
18. Turned off Next `cacheComponents`: auth-gated dynamic pages don't benefit and it broke prerendering.
19. **No `proxy.ts` for now.** Netlify CLI 23.6 on Node 24 fails to bundle Next 16's Node-runtime proxy as an edge function (Deno `findSourceMap` error). Without it Supabase session cookies aren't refreshed on page loads, so a signed-in user is sent back to `/login` after the access token expires (~1h). Re-add the proxy (it's in git history, commit "Slice 2") once deploys run from Netlify's own build or the CLI is fixed.
20. **Engine reads programs from `lib/programs.generated.json`**, built from `/programs/*.yaml` by `prebuild`/`pretest` (schema-validated; build fails on a bad program). Each program carries a content-hash `version`. Loading into the `programs`/`program_versions` tables is deferred to Slice 5, when evaluations need the foreign key.
21. **Hard safety net in the engine:** a program with `confidence: needs_review` can never return eligible/likely, regardless of its YAML. Needs-human-review results are `reviewer_only`.
22. **Money totals:** the plan total counts eligible + likely only. Needs-review values are reported separately as "pending review". Values with unverified inputs flag the total as provisional. Programs without a verified value formula (Extra Help, Apple Health, property tax) show no dollar figure rather than an invented one.
23. **Ages are bracketed** (birth year only): "certain" vs "possible" age, with the uncertain band sent to review.
24. **Household of 3+ people goes to review** for Medicare programs because unit composition (who is the spouse) isn't collected yet.
25. **Packets are "answers sheets", not filled official forms.** I haven't verified any agency's fillable PDF URL or field names, and rule 3 says don't invent. Each sheet lays out the household's answers, why we think they qualify, a blank line for SSN/Medicare number, the evidence checklist, and how to apply. Official-form filling is added per program once a form is verified.
26. **Packet and checklist gate:** only after `households.reviewed_at` is set (clients can't write it; reviewer console sets it in Slice 5), only for `verified` programs with eligible/likely results. Until Slice 5 no household can get a packet; `scripts`-free demo is the unit test.
27. **Extraction model: `claude-sonnet-5-5`** (override with `EXTRACTION_MODEL`), effort `low`, structured output via `messages.parse` + zod (Sonnet 5.5 rejects forced tool use). I chose Sonnet over the Opus default to keep per-household API cost down for the margin test; switch if accuracy disappoints. Field names are an allow-list; SSN-like or 9+ digit values are dropped server-side. Refusals mark the document "failed" for manual review (no server-side fallback).
28. **Human confirmation:** extracted values start unconfirmed; the household edits and ticks what is right; `confirmedFields()` is the only reader. Reviewer re-verification of evidence for the ledger arrives in Slice 5.
29. **Known gap:** `extraction_usage` (token counts for the margin calculation) is written by the user's own session under RLS, so a determined user could alter their own usage numbers. Move to a service-role write when the service key is in place.
30. **Storage:** private `documents` bucket, 10 MB, PDF/JPG/PNG only, path `<household_id>/<uuid>.<ext>`, owner/staff RLS, viewing via 5-minute signed URLs, direct browser upload (avoids function body limits).
31. **Staff roles by email allow-list** (`staff_emails`, applied when a profile is first created; magic link proves the email). Seeded: `dekpep@gmail.com` = admin. Add reviewers with `insert into staff_emails values ('x@y.com','reviewer')` before they first sign in (or `update profiles set role=...` after).
32. **Evaluations are snapshotted when a reviewer starts a review** (no service key needed), with the program version hash. Programs are not yet in DB tables; `program_id` + version hash is the reference (decision 20 stands).
33. **Reviewer approval releases results.** Approving a "needs human review" item requires the reviewer to state the outcome (eligible/likely/unlikely). Households see only approved evaluations, and only after the whole household review is finished (`approve_household()`, staff-only, refuses while any item is pending or escalated). This is how `needs_review` programs can reach a household: only through a person.
34. **Ledger is append-only and PII-free, with no foreign keys**, so it survives a household deletion request (sponsor guarantee reporting needs it). Attorney question added to the compliance list: is retaining de-identified outcome rows after deletion acceptable?
35. **"Verified" is enforced by the database:** `approved` entries need basis `determination_letter`, `received` entries need `confirmed_receipt`, both need an evidence document and the verifying staff member (`verified_by` must be the inserting user). Estimates never count. Latest verified entry per claim is the verified value.
36. **Claim status:** households can only move recommended/prepared → prepared/submitted (DB trigger); staff set anything. Every status change is written to `audit_log`.
37. **Reviewer time** is measured in the browser (visible-tab seconds), clamped to 2 hours, stored on the `reviews` row at finish/escalate. Escalation is a log entry plus leaving the household in the queue; there is no separate senior-reviewer role yet.
38. **Queue order:** estimated yearly value (likely, confirmed + pending), then days waiting.
39. **White-label flow:** `/s/<slug>` (sponsor name and https logo, counts a visit) -> `/intake?org=<slug>` -> login -> consent screen with an unchecked, optional "let {sponsor} see my individual results" box. Household, org link and consent are written together by the `create_household()` database function; a client cannot attach itself to an org. Logos are set by admin (`organizations.logo_url`); there's no upload UI yet.
40. **Sponsors see aggregates only**, via `sponsor_stats()` (viewer of that org or staff). Individual rows come from `sponsor_shared_households()` and only for households whose latest consent shares with that org, with city and claim statuses but no names. Program-level rows with fewer than 5 claims are hidden in the dashboard and exports.
41. **Guarantee definitions (for the Sponsor Agreement draft):** *Enrolled household* = completed the questionnaire through the sponsor link. *Verified gain* = latest approved (determination letter) or received (confirmed receipt) ledger value per claim, with evidence and a staff verifier. Test = verified total / enrolled households (zeros included) vs 5x the per-household fee.
42. **Exposure is capped at fees paid.** Uncapped, a pilot with no outcomes would owe up to $495 per household against a $99 fee. I capped the dashboard's "credit/refund exposure" at fees paid and flagged it for you and counsel; the contract wording is yours to decide.
43. **"Invited" in the funnel = opened the enrollment link** (anonymous counter, no identifiers). We don't know who a sponsor sent the link to.
44. **Reports** are a snapshot at download time (PDF and CSV) with 30-day deltas for new households and verified value; true month-end snapshots would need stored history (Slice 7 if wanted). Sponsor logins are provisioned with `scripts/sponsor-invoice.ts --viewer email`, which adds a `sponsor_viewer` row to `staff_emails`.
45. **Deleted households:** ledger rows survive (decision 34), so after a deletion the verified total still counts but the enrolled count drops, which inflates the average slightly. Acceptable for pilot scale; revisit with counsel.
46. **20 programs, 8 verified.** Verified: Medicare Savings Program, Extra Help, Basic Food, Lifeline, ORCA LIFT, LIHEAP (income screen), TPU, Seattle UDP. The other 12 (including Apple Health and the property-tax exemptions) are `needs_review` stubs that can only route to a reviewer. Details and gaps: `PROGRAMS_VERIFICATION.md`. A dead "approved for Basic Food" shortcut in Lifeline and ORCA was removed after writing tests showed it could never fire (SNAP's net limit is below both programs' limits).
47. **Reminders:** a daily Netlify scheduled function calls `/api/cron/reminders` (bearer `CRON_SECRET`) which finds due reminders with the pure function `dueReminders()`, claims a `reminder_log` row first (so a retry can't double-send), then sends through Resend's HTTP API. Kinds: docs missing (7+ days, no uploads, max 3), agency needs info (weekly, max 4), renewal 30 and 7 days. Email only; no SMS. `?dry=1` lists without sending. Untested against real Resend (no key).
48. **Kill-criteria dashboard (`/admin/kill`)** shows completion rate, verified-gain multiple, and margin with red/green/no-data lights. Margin uses assumptions: reviewer wage $40/hr and Sonnet-class API prices ($2 in / $10 out per million tokens), overridable by env. It ignores Stripe fees, hosting and your own time.
49. **Admin screens are read-mostly:** programs (confidence, last verified, stale > 1 year), sponsors, payments. Program rules are edited in git (YAML), not in the browser, so every change has history and a version hash. Sponsor creation stays a script.
50. **Seed data is SQL you run yourself** (`npm run seed:sql`), not auto-inserted. I confirmed the generated inserts satisfy every table constraint in a rolled-back run against the dev database.
51. **Phase 2 design (see docs/DESIGN_BRIEF.md, BRAND.md, DESIGN_QA.md):** tokens live in `globals.css`; Fraunces + Atkinson via `next/font`; display settings (larger text, high contrast) are a `ui` cookie read in the root layout. That makes every page dynamic. Sponsor landing is `/for-sponsors`; `/sponsor` stays the logged-in redirect. Claim tracker is new at `/track`. `/design` is a public, noindex component specimen.
52. **Intake has no live dollar preview** (would release unreviewed results; DECISIONS 33). Revisit if you want one.
